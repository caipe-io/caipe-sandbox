# Portal sidecars

`extraContainers`, `extraVolumes`, and `extraServicePorts` accept native Kubernetes container, volume, and Service port objects. They default to empty arrays. `extraObjects` can provide supporting ConfigMaps or other Kubernetes objects. Container and volume names and Service port names must not collide with chart-managed names. The Pod's security context applies to sidecars; choose images and container security settings compatible with non-root execution and the cluster's policies. Pin images by digest.

For an internal TLS endpoint, an operator can add a TLS-terminating proxy in the portal Pod and expose its port through the portal Service. Configure the proxy to forward only the intended paths to `127.0.0.1:8000`, including WebSocket upgrades, and reject all others. Configure long-lived connection timeouts and graceful shutdown appropriately. The existing HTTP Service port remains available; use network policies to restrict it as appropriate. A path restriction at the proxy does not replace portal authentication or authorization.

Provision a server certificate and private key using the operator's existing certificate infrastructure, mount the Secret only in the proxy, and ensure the certificate covers the exact Service DNS name used by clients. Distribute the issuing CA to clients through their supported trust mechanism, without disabling certificate verification. The chart does not issue certificates, configure client trust, or trigger a rollout when an external Secret changes; the operator must arrange certificate rotation and proxy reload or Pod restart. Test DNS, certificate validation, WebSocket upgrade, access controls, and network policies end-to-end before relying on the endpoint.
